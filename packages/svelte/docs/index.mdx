`@lunora/svelte` is the Svelte adapter for Lunora. It's a thin layer over the
framework-neutral [`@lunora/client`](/docs/packages/client), which owns the
WebSocket transport, subscription registry, offline queue, and delta-merge. The
adapter re-expresses that contract as runes-native handles: a live query is an
object whose `current` re-runs every reader on each server delta; an optimistic
mutation is a handle of reactive properties plus an awaitable `mutate`.

Reactivity is [`createSubscriber`](https://svelte.dev/docs/svelte/svelte-reactivity#createSubscriber)
from `svelte/reactivity`, so the package stays plain `.ts` — no `.svelte` or
`.svelte.ts` compiler step is required to build or use it — while every handle
is tracked by `$derived`, `$effect`, and template reads like any other rune.

<Callout type="warn">
    **Preview.** The Svelte adapter exists and exposes the same hydrate-then-subscribe handoff as React, but it is **preview** maturity and not yet proven
    end-to-end against a running app. The React adapter is the only one verified through the full live-loader path. See [Bring your
    framework](/docs/frameworks/bring-your-framework).
</Callout>

```svelte
<!-- +layout.svelte — provide the client once at the root. -->
<script lang="ts">
    import type { Snippet } from "svelte";

    import { LunoraClient } from "@lunora/client";
    import { setLunoraClient } from "@lunora/svelte";

    let { children }: { children: Snippet } = $props();

    setLunoraClient(new LunoraClient({ url: import.meta.env.VITE_LUNORA_URL }));
</script>

{@render children()}
```

## Reading a handle

Every reactive value on a handle is a getter. Read it **off the handle** —
`messages.current`, `send.pending` — in a template, a `$derived`, or an
`$effect`.

<Callout type="warn">
    Do not destructure a reactive member. `const {pending} = mutation(...)` copies the value once, at that moment, and it never updates. Destructuring the plain
    functions (`mutate`, `loadMore`, `teardown`) is fine.
</Callout>

```svelte
<script lang="ts">
    import { mutation, query } from "@lunora/svelte";

    import { api } from "$lib/_generated/api";

    const messages = query(api.messages.list, { channelId: "general" });
    const send = mutation(api.messages.send);

    // Handles compose with `$derived` like any other reactive read.
    const unread = $derived((messages.current ?? []).filter((m) => !m.read).length);
</script>

<h2>Inbox ({unread})</h2>
<button disabled={send.pending} onclick={() => send.mutate({ channelId: "general", text: "hi" })}>Send</button>
```

## Exports

| Symbol             | Kind     | Role                                                                                   |
| ------------------ | -------- | -------------------------------------------------------------------------------------- |
| `setLunoraClient`  | function | Publish the shared `LunoraClient` on Svelte context. Call once high in the tree.       |
| `getLunoraClient`  | function | Read the `LunoraClient` from context. Throws if none was set.                          |
| `query`            | function | Live query; `current` is the server value. Sharing one handle shares one subscription. |
| `mutation`         | function | Optimistic mutation handle: `{ data, error, pending, mutate, reset }`.                 |
| `action`           | function | Action handle: `{ data, error, pending, call, reset }`. No optimistic options.         |
| `hydratePreloaded` | function | Seed a handle synchronously from an SSR `Preloaded` token, then attach the socket.     |

The table above lists the core handful. The package also exports the live
handles covered under [Additional handles](#additional-handles):
`subscription`, `paginatedQuery`, `infiniteQuery`, `presence`, `rateLimit`,
`auth`, and `connectionStatus`.

Re-exported types from `@lunora/client`: `ArgsOf`, `ConnectionStatus`,
`FunctionReference`, `LunoraClient`, `MutationCallOptions`, `Preloaded`,
`ReturnOf`, plus the adapter's own `QueryHandle`, `QueryOptions`,
`MutationHandle`, and `ActionHandle`.

<Callout type="info">
Unlike React/Solid/Vue (which use `useLunora`), the Svelte provider accessor is
the idiomatic `getLunoraClient`. There is no `<LunoraProvider>` component; you
publish the client with `setLunoraClient` during component init.
</Callout>

## Provider — `setLunoraClient` / `getLunoraClient`

`setLunoraClient(client)` publishes the `LunoraClient` on the Svelte component
context. Call it once, high in the tree (typically your root `+layout.svelte` or
`App.svelte`), during component initialisation: `setContext` must run while the
component is being constructed. This is the Svelte analogue of mounting React's
`LunoraProvider`.

`getLunoraClient()` reads it from the nearest ancestor and throws if no provider
was set, so a missing client fails loudly rather than as a later `undefined`
dereference. Most code never calls it directly; `query` / `mutation` /
`hydratePreloaded` resolve the ambient client for you.

## `query(fn, args, options?)`

Opens a live query. `current` holds `undefined` until the first response lands,
then the latest server value; every reader re-runs on each delta. This is the
Svelte equivalent of React's `useQuery`.

The subscription opens lazily, on the first **tracked** read of `current` (from
a template, a `$derived`, or an `$effect`), and tears down once every effect
that read it is destroyed. So a handle nobody reads opens no socket, an
unmounting component releases its subscription, and a server render — where
nothing tracks — opens nothing. Sharing one handle across several components
shares a single underlying subscription (the client de-dupes by
`(fn, args, shardKey)`).

```svelte
<script lang="ts">
    import { query } from "@lunora/svelte";

    import { api } from "$lib/_generated/api";

    const messages = query(api.messages.list, { channelId: "general" });
</script>

<ul>
    {#each messages.current ?? [] as m (m._id)}
        <li>{m.text}</li>
    {/each}
</ul>
```

`query` is overloaded: pass `client` explicitly as the first argument, or omit it
to resolve the ambient client published by `setLunoraClient`.

```ts
// Ambient client (default):
query(api.messages.list, { channelId });
// Explicit client:
query(client, api.messages.list, { channelId });
```

`options` accepts `{ shardKey }` to route to a specific shard when the target
function is `.shardBy(...)`-partitioned, and `{ onError }`, a callback invoked
when the underlying subscription reports an error.

### Args that change

Build the handle inside a `$derived.by`. Each change constructs a fresh handle
against the new args, and the subscription the previous one held is released
when the reading effect re-runs — no separate reactive-args API, and no stale
subscription to clean up.

```svelte
<script lang="ts">
    import { query } from "@lunora/svelte";

    import { api } from "$lib/_generated/api";

    let channelId = $state("general");

    const messages = $derived.by(() => query(api.messages.list, { channelId }));
</script>

<ul>
    {#each messages.current ?? [] as m (m._id)}
        <li>{m.text}</li>
    {/each}
</ul>
```

The same shape applies to `subscription` and `paginatedQuery` (where a rebuild
also resets pagination to the first page).

Pass `"skip"` as `args` to keep the handle but leave the subscription dormant
(`current` stays `undefined`, no socket opens) — useful for a query gated on
auth or a route param, matching React/Vue/Solid's `useQuery`.

## `mutation(fn)`

Creates an optimistic `MutationHandle` for a mutation reference:

```ts
interface MutationHandle<F> {
    readonly data: ReturnOf<F> | undefined; // latest resolved value
    readonly error: Error | undefined; // latest error
    readonly pending: boolean; // true while any call from this handle is in flight (ref-counted)
    mutate: (args, options?) => Promise<ReturnOf<F>>; // awaitable; resolves with the server value, rejects on failure
    reset: () => void; // clear data/error back to idle
}
```

`pending` is ref-counted across overlapping invocations of the same handle, so
read `handle.pending` to disable a button until the last concurrent call
settles. `mutation` is overloaded the same way as `query`: pass `client`
explicitly or omit it to use the ambient client.

```svelte
<script lang="ts">
    import { mutation } from "@lunora/svelte";

    import { api } from "$lib/_generated/api";

    const send = mutation(api.messages.send);
</script>

<button disabled={send.pending} onclick={() => send.mutate({ channelId: "general", text: "hi" })}>Send</button>
{#if send.error}<p>{send.error.message}</p>{/if}
```

### Optimistic updates

Optimistic updates stay client-owned and are passed **per call** in `mutate`'s
options: the `optimistic` / `optimisticUpdate` options are applied and rolled
back by the client against the live query subscriptions, exactly as in the React
adapter. Any `query` / `hydratePreloaded` handle reading the same data reflects
the change immediately and reverts on failure.

```ts
await send.mutate(
    { channelId, text },
    {
        optimisticUpdate: (store) => {
            const current = store.getQuery(api.messages.list, { channelId }) ?? [];
            store.setQuery(api.messages.list, { channelId }, [...current, draft]);
        },
    },
);
```

## `action(fn)`

Creates an `ActionHandle` for an action reference — the same shape as
`MutationHandle`, with `call` in place of `mutate`:

```ts
interface ActionHandle<F> {
    call: (args, options?) => Promise<ReturnOf<F>>; // awaitable; resolves with the server value, rejects on failure
    readonly data: ReturnOf<F> | undefined; // latest resolved value
    readonly error: Error | undefined; // latest error
    readonly pending: boolean; // true while any call from this handle is in flight (ref-counted)
    reset: () => void; // clear data/error back to idle
}
```

`action` is overloaded the same way as `query` and `mutation`: pass `client`
explicitly or omit it to use the ambient client.

```svelte
<script lang="ts">
    import { action } from "@lunora/svelte";

    import { api } from "$lib/_generated/api";

    const verify = action(api.commands.run);
</script>

<button disabled={verify.pending} onclick={() => verify.call({ command: "lunora", args: ["verify"] })}>Verify</button>
{#if verify.error}<p>{verify.error.message}</p>{/if}
```

Per-call options are `{ shardKey }` only. Unlike `mutation` there are no
`optimistic` / `optimisticUpdate` options: an optimistic update patches the
subscription cache on the assumption a write will land, and an action is not a
write — it runs in the Worker, may call a third party, and has no declared
effect on any query.

## Reactive loaders — `hydratePreloaded`

The SSR-seed-to-live handoff, the Svelte equivalent of React's
`usePreloadedQuery`. Run the query on the server with `preloadQuery` (from
`@lunora/svelte/server`) in a SvelteKit `+page.ts` / `+layout.ts` `load`, hand the
serializable `Preloaded` token to the client, and `hydratePreloaded` seeds
`current` **synchronously** with `preloaded.value`, so the first read during
hydration returns the server value with no loading flash and no hydration
mismatch. On the first tracked read in the browser a live WS subscription
attaches and every subsequent delta re-runs the readers, exactly like a plain
`query` handle.

```svelte
<script lang="ts">
    import { hydratePreloaded } from "@lunora/svelte";

    // `data.preloaded` came from a +page.ts load → preloadQuery
    let { data } = $props();

    const posts = $derived(hydratePreloaded(data.preloaded));
</script>

<ul>
    {#each posts.current as p (p._id)}
        <li>{p.title}</li>
    {/each}
</ul>
```

Pass `client` as a second argument to override the ambient client. On the server
nothing tracks the read, so the subscription never opens and the handle simply
reports the seeded value; the token's `value` is the single source of truth for
the first paint.

## `@lunora/svelte/server`

Server-side preload helpers, re-exported from `@lunora/client/ssr`, the
framework-neutral server contract shared by every adapter. This entry opens no
WebSocket and touches no browser globals, so it is safe to import from a
SvelteKit `+page.ts` / `+layout.ts` `load`.

```ts
// src/routes/posts/+page.ts
import { createServerClient, preloadQuery } from "@lunora/svelte/server";

import { api } from "$lib/_generated/api";

export async function load({ fetch }) {
    // Forward SvelteKit's fetch so the session cookie rides along.
    const client = createServerClient({ url: import.meta.env.VITE_LUNORA_URL, fetch });
    const preloaded = await preloadQuery(client, api.posts.list, {});

    return { preloaded };
}
```

Exports: `createServerClient`, `preloadQuery`, `serializePreloaded`,
`deserializePreloaded`, `preloadedQueryResult`, `getServerSession`, plus the
`Preloaded` / `ServerClientOptions` / `ServerSession` types.

## Single-worker composition

SvelteKit owns its Cloudflare build via `@sveltejs/adapter-cloudflare`, so
Lunora cannot own the worker entry; instead it **injects** its realtime plane
into the worker SvelteKit emits, via `buildFrameworkWorker` on the generated
app (`withFrameworkWorker` from [`@lunora/runtime`](/docs/packages/runtime)
under the hood): the reserved `/_lunora/*` endpoints hit Lunora and
everything else delegates to SvelteKit. One worker, one deploy. See
[Bring your framework](/docs/frameworks/bring-your-framework) for the full
composition and a working example.

## Additional handles

Beyond `query` / `mutation`, the package exports the same surface the React
adapter exposes as hooks. Each resolves the ambient client by default or takes
an explicit `client` as its first argument. Handles that own a timer or listener
(`presence`, `rateLimit`) return a `teardown()`; call it from `onDestroy`.

### `subscription(fn, args, options?)`

A raw live subscription: `data` holds the latest server push (`undefined` until
the first), `error` the last subscription error. Both share one subscription,
which opens on the first tracked read of either. Pass `"skip"` as `args` to keep
the handle but leave the subscription dormant. Options: `{ shardKey, onError }`.

```svelte
<script lang="ts">
    import { subscription } from "@lunora/svelte";
    import { api } from "$lib/_generated/api";

    const live = subscription(api.messages.live, { room: "general" });
</script>

{#if live.error}<p>{live.error.message}</p>{/if}
{#each live.data ?? [] as m (m._id)}<li>{m.text}</li>{/each}
```

### `paginatedQuery(fn, args, { initialNumItems })`

A cursor-paginated live query. `args` is the function's args minus
`paginationOpts` (the framework supplies the cursor), or `"skip"`. The handle is
`{ results, status, isLoading, loadMore }`: `results` is the flattened items
across every loaded page; `status` is `"LoadingFirstPage" | "LoadingMore" |
"CanLoadMore" | "Exhausted"`; `loadMore(n)` appends the next page (a no-op unless
`status === "CanLoadMore"`).

```svelte
<script lang="ts">
    import { paginatedQuery } from "@lunora/svelte";
    import { api } from "$lib/_generated/api";

    const page = paginatedQuery(api.messages.page, { room: "general" }, { initialNumItems: 20 });
</script>

{#each page.results as m (m._id)}<li>{m.text}</li>{/each}
<button disabled={page.status !== "CanLoadMore"} onclick={() => page.loadMore(20)}>Load more</button>
```

`infiniteQuery` is the TanStack-Query-shaped variant: `{ pages, status,
isLoading, hasNextPage, isFetchingNextPage, fetchNextPage }`, where `pages` keeps
each loaded page as its own inner array.

### `presence(roomId, options)`

Collaborative awareness: the client half of the server `definePresence` preset.
Drives a heartbeat mutation (on call, on an interval, and on tab re-focus) and
subscribes to the room's `listPresent` query. Options: `{ heartbeat, listPresent,
sessionId?, data?, intervalMs?, shardKey? }`, where `heartbeat` and `listPresent`
are `api.*` references. The handle is `{ present, sessionId, setData, teardown }`.

```svelte
<script lang="ts">
    import { onDestroy } from "svelte";
    import { presence } from "@lunora/svelte";
    import { api } from "$lib/_generated/api";

    const room = presence("room-42", {
        heartbeat: api.presence.heartbeat,
        listPresent: api.presence.listPresent,
        data: { name: "Ada" },
    });
    onDestroy(room.teardown);
</script>

{#each room.present ?? [] as p (p.userId)}<span>{p.data?.name}</span>{/each}
```

### `rateLimit(config, options?)`

A client-side mirror of a server rate limit for instant UX: disable a button or
show a countdown without a round-trip. It runs the same token-bucket /
fixed-window math as `@lunora/ratelimit`, but the server stays authoritative. The
handle is `{ ok, disabled, retryAfter, check, consume, reset, teardown }`, where
`ok` / `disabled` / `retryAfter` are reactive and `consume(count?)` records a
local hit. Pass a stable `config` reference (a module constant). Options: `{ now?,
tickMs? }`.

```svelte
<script lang="ts">
    import { onDestroy } from "svelte";
    import { rateLimit } from "@lunora/svelte";

    const limit = rateLimit({ kind: "token bucket", rate: 5, period: 60_000 });
    onDestroy(limit.teardown);
</script>

<button disabled={limit.disabled} onclick={() => limit.consume()}>Send {limit.disabled ? `(${limit.retryAfter}ms)` : ""}</button>
```

### `auth(client?)` and `connectionStatus(client?)`

`auth` returns `{ user, token, setToken }`: `user` and `token` are reactive
(`null` when signed out), and `setToken(jwt)` sets the token on the client after
sign-in. `connectionStatus` returns a handle whose `current` is the aggregate
live-socket state (`idle` → `connecting` → `connected` → `offline`), for driving
a connection indicator.

```svelte
<script lang="ts">
    import { auth, connectionStatus } from "@lunora/svelte";

    const session = auth();
    const status = connectionStatus();
</script>

{#if session.user}Signed in as {session.user.name}{/if}
<span data-status={status.current}>{status.current}</span>
```
